# Booking Service

## Current status

S6-01 through S6-07 are complete. Protected APIs include `POST/GET /api/v1/booking-requests`, `GET /api/v1/booking-requests/{id}`, `POST /api/v1/booking-requests/{id}/submit`, `POST /api/v1/booking-requests/{id}/decision`, `POST /api/v1/bookings/direct`, and the reservation lifecycle operations `POST /api/v1/reservations/{reservationId}/check-in` and `/complete`. Creation validates request data and current Organization, Room, and Scheduling owner data before storing a `DRAFT`; only its active requester can submit it, which revalidates current policy and transitions it to `PENDING_APPROVAL`. Scoped Admin/Super Admin approval and rejection record one decision per request, with Identity-derived actor/time and an optional comment. Requesters cannot decide their own requests. Approval revalidates current Identity authorization, Organization, Room, Scheduling constraints/rules, and Booking-owned occupancy; within one transaction it stores the decision, creates a confirmed reservation using the current release buffer, and creates a PRIVATE meeting with the requester as accepted organizer participant. Rejection records the decision and state without creating a reservation or meeting. The direct-booking route supports authorized Admin/Super Admin and eligible Secretary callers. The active Room rule applies irrespective of initiator: when `approvalRequired=true`, only a `PENDING_APPROVAL` request is created, with no reservation or meeting; a different authorized approver must decide it. When approval is not required, Booking revalidates owner data and atomically confirms the reservation, each bounded occurrence, and private meeting.

Recurring acceptance uses the persisted Scheduling RRULE and IANA timezone, with Scheduling's one-year/365-date bounds. Booking validates every evaluated occurrence against the same-day timezone-local interval, the effective room policy, Room's existing protected maintenance-period API, and Booking-owned occupancy before writing. If any occurrence requires approval, the whole series uses the existing pending-approval workflow; the greatest applicable release buffer is used consistently for the series. The user-approved `reservation_occurrence` table stores one row per evaluated local date, and its PostgreSQL GiST exclusion constraint remains the final concurrent-conflict barrier. One transaction creates the series reservation, all occurrence rows, decision, meeting, organizer participant, and request transition. Scheduling and maintenance conflicts reject the series before writes with occurrence-specific stable errors; Booking occupancy conflicts roll back the whole series and return `ROOM_OCCUPANCY_CONFLICT` with affected local dates in the shared error message. PostgreSQL exclusion conflicts and deadlocks during overlapping writes normalize to that same stable conflict. Request idempotency and locked request state prevent duplicate acceptance.

Identity returns trusted display data only for authorized actions. Booking derives actor identity and evaluates current permissions, privilege, and building/department scope; client-supplied actor, request type, approval result, and status are never authoritative. Booking forwards the caller bearer token to Identity, Organization, Room, and Scheduling and fails closed on missing, denied, inconsistent, or unavailable authoritative results. A global interceptor protects every `/api/v1/**` handler, including `OPTIONS`. Check-in is allowed only for a `CONFIRMED` reservation and sets `checkedInAt` from the server clock; completion is allowed only after check-in and sets `completedAt` from the server clock. Requests do not accept actor IDs or timestamps. The transitions are row-locked and terminal `CANCELLED`/`RELEASED` reservations cannot be reopened. The approved nullable `reservation.completed_at TIMESTAMP WITH TIME ZONE` column is required iff status is `COMPLETED`, enforced by Flyway V3. No automatic missed-check-in or overdue status transition/release occurs. Reservation and occurrence occupancy remains half-open and includes the release buffer (five minutes by default); PostgreSQL GiST exclusion constraints remain the final overlap barrier. Lifecycle APIs are service-level protected routes only, with no API Gateway route. Cancellation, expiration processing, extensions, share links, and the Booking occupancy provider remain future Stage 6 requirements.

S6-07 verification passed: the focused Booking lifecycle selection passed 37 tests, Identity passed 48, common-web passed 6, and the full 11-project backend reactor passed 244 tests, with zero failures, errors, or skips.

The user accepted Stage 5, approved the Stage 6 checklist, and selected all-or-nothing acceptance for recurring bookings: validate every occurrence, report occurrence-specific conflicts, and persist no occurrence if any occurrence fails. The user explicitly approved the S6-05 `reservation_occurrence` ERD extension; it adds one child row per scheduled occurrence and a room/range GiST exclusion barrier while keeping `reservation` as the series-level record. The checklist is maintained in [Backend Documentation](../Documentation.md#stage-6-requirement-checklist-approved). Identity evaluates current account status, permissions, scope, and privilege through protected `POST /api/v1/internal/authorization/booking`; see the Identity [authorization policy](../identity-service/AUTHORIZATION.md). Booking APIs remain unrouted in the API Gateway.

## Ownership and constraints

- Booking owns requests, approval decisions, reservations, occurrence occupancy, meetings, and participants. Request creation idempotency is enforced; cancellation, extensions, share links, and the authoritative occupancy snapshot remain future Stage 6 work.
- Booking must use Identity, Organization, Room, and Scheduling owner APIs for authoritative cross-service data and decisions. It must not read or write another service's database.
- Confirmed reservation occupancy and concurrent same-room overlap prevention belong to Booking. Each `reservation_occurrence` stores a half-open interval including the configured release buffer; its GiST exclusion constraint is the final same-room concurrency barrier. The reservation range has its own GiST exclusion constraint for direct/single-occurrence reservations; `reservation` remains the series-level record and keeps its first-occurrence compatibility range.
- Approval-time overlap checks use Booking-owned occurrence data; the PostgreSQL occurrence exclusion constraint is the final concurrent-write barrier. The decision, series reservation, every occurrence, meeting, organizer participant, and request transition are committed or rolled back together.
- Booking's future internal occupancy provider is a dependency of Scheduling availability. Until implemented, candidate-producing availability searches fail closed.
- All Booking business operations require server-side authorization except the narrowly scoped public share-token read, if approved and implemented. Stage 11 owns Gateway routing.
- The decision endpoint and reservation lifecycle operations are protected by the `/api/v1/**` bearer/Identity authorization guard and are not configured on the API Gateway.
- `POST /api/v1/bookings/direct` is protected by the same guard, resolves current Identity authority before owner-data validation, rechecks VIP eligibility from the authoritative Room result, and applies the active room's approval requirement to Admin, Super Admin, and Secretary initiators alike. It is not configured on the API Gateway.
- `POST /api/v1/reservations/{reservationId}/check-in` and `/complete` require current Identity authorization and persisted organizer/building/department facts. Identity allows an organizer only within their current scope, a lifecycle manager only within assigned building scope, or a global system administrator. The server sets lifecycle timestamps; invalid state transitions return `RESERVATION_STATE_CONFLICT`. Neither route is configured on the API Gateway.
- The approved ERD must not be changed without explicit user approval. Any demonstrated need for an ERD change must be proposed for approval before editing it.

## Current module configuration

The application listens on `${BOOKING_SERVICE_PORT:8085}` and exposes Actuator `health` and `info`. PostgreSQL settings are `${BOOKING_DB_URL:jdbc:postgresql://localhost:5432/roomiq_booking}`, `${BOOKING_DB_USERNAME:roomiq}`, and `${BOOKING_DB_PASSWORD:roomiq}`. Integration base URLs are `${IDENTITY_SERVICE_URL:http://localhost:8081}`, `${ORGANIZATION_SERVICE_URL:http://localhost:8082}`, `${ROOM_SERVICE_URL:http://localhost:8083}`, and `${SCHEDULING_SERVICE_URL:http://localhost:8084}`. Hibernate validates the Flyway-managed schema and does not create/update tables. See [pom.xml](pom.xml), [application.yml](src/main/resources/application.yml), [V1__booking_schema.sql](src/main/resources/db/migration/V1__booking_schema.sql), and [BookingServiceApplication.java](src/main/java/rw/rra/roomiq/booking/BookingServiceApplication.java).
