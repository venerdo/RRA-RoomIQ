# Booking Service

## Current status

S6-01 through S6-04 are implemented; S6-05 is in progress. Protected APIs are `POST/GET /api/v1/booking-requests`, `GET /api/v1/booking-requests/{id}`, `POST /api/v1/booking-requests/{id}/submit`, and `POST /api/v1/booking-requests/{id}/decision`. Creation validates request data and current Organization, Room, and Scheduling owner data before storing a `DRAFT`; only its active requester can submit it, which revalidates current policy and transitions it to `PENDING_APPROVAL`. Scoped Admin/Super Admin approval and rejection record one decision per request, with Identity-derived actor/time and an optional comment. Requesters cannot decide their own requests. Approval revalidates current Identity authorization, Organization, Room, Scheduling constraints/rules, and Booking-owned occupancy; within one transaction it stores the decision, creates a confirmed reservation using the current release buffer, and creates a PRIVATE meeting with the requester as accepted organizer participant. Rejection records the decision and state without creating a reservation or meeting. S6-05 adds the user-approved `reservation_occurrence` child model; a recurring reservation stores one row per evaluated local date and protects every buffered range with a PostgreSQL GiST exclusion constraint. Direct-booking API outcomes, current Identity authorization, and the Secretary approval-required policy are being implemented. Row locking and database uniqueness/exclusion constraints reject stale, repeated, and competing decisions without partial writes. Identity returns trusted display data only for an authorized confirmation action. Booking derives actor identity and evaluates current permissions, privilege, and building/department scope; client-supplied actor, request type, approval result, and status are never authoritative. Booking forwards the caller bearer token to Identity, Organization, Room, and Scheduling and fails closed on missing, denied, inconsistent, or unavailable authoritative results. A global interceptor protects every `/api/v1/**` handler, including `OPTIONS`. Cancellation, expiration processing, extensions, share links, and remaining Booking workflows are future Stage 6 requirements; no Gateway route is configured.

The user accepted Stage 5, approved the Stage 6 checklist, and selected all-or-nothing acceptance for recurring bookings: validate every occurrence, report occurrence-specific conflicts, and persist no occurrence if any occurrence fails. The user explicitly approved the S6-05 `reservation_occurrence` ERD extension; it adds one child row per scheduled occurrence and a room/range GiST exclusion barrier while keeping `reservation` as the series-level record. The checklist is maintained in [Backend Documentation](../Documentation.md#stage-6-requirement-checklist-approved). Identity evaluates current account status, permissions, scope, and privilege through protected `POST /api/v1/internal/authorization/booking`; see the Identity [authorization policy](../identity-service/AUTHORIZATION.md). Booking APIs remain unrouted in the API Gateway.

## Ownership and constraints

- Booking owns requests, approval decisions, reservations, meetings, and participants. Cancellation, extensions, share links, idempotency, and the authoritative occupancy snapshot remain future Stage 6 work.
- Booking must use Identity, Organization, Room, and Scheduling owner APIs for authoritative cross-service data and decisions. It must not read or write another service's database.
- Confirmed reservation occupancy and concurrent same-room overlap prevention belong to Booking. Each `reservation_occurrence` stores a half-open interval including the configured release buffer; its GiST exclusion constraint is the final same-room concurrency barrier. `reservation` remains the series-level record and keeps its first-occurrence compatibility range.
- Approval-time overlap checks use Booking-owned occurrence data; the PostgreSQL occurrence exclusion constraint is the final concurrent-write barrier. The decision, series reservation, every occurrence, meeting, organizer participant, and request transition are committed or rolled back together.
- Booking's future internal occupancy provider is a dependency of Scheduling availability. Until implemented, candidate-producing availability searches fail closed.
- All Booking business operations require server-side authorization except the narrowly scoped public share-token read, if approved and implemented. Stage 11 owns Gateway routing.
- The decision endpoint is protected by the `/api/v1/**` bearer/Identity authorization guard and is not configured on the API Gateway.
- The approved ERD must not be changed without explicit user approval. Any demonstrated need for an ERD change must be proposed for approval before editing it.

## Current module configuration

The application listens on `${BOOKING_SERVICE_PORT:8085}` and exposes Actuator `health` and `info`. PostgreSQL settings are `${BOOKING_DB_URL:jdbc:postgresql://localhost:5432/roomiq_booking}`, `${BOOKING_DB_USERNAME:roomiq}`, and `${BOOKING_DB_PASSWORD:roomiq}`. Integration base URLs are `${IDENTITY_SERVICE_URL:http://localhost:8081}`, `${ORGANIZATION_SERVICE_URL:http://localhost:8082}`, `${ROOM_SERVICE_URL:http://localhost:8083}`, and `${SCHEDULING_SERVICE_URL:http://localhost:8084}`. Hibernate validates the Flyway-managed schema and does not create/update tables. See [pom.xml](pom.xml), [application.yml](src/main/resources/application.yml), [V1__booking_schema.sql](src/main/resources/db/migration/V1__booking_schema.sql), and [BookingServiceApplication.java](src/main/java/rw/rra/roomiq/booking/BookingServiceApplication.java).
