# Booking Service

## Current status

S6-01 through S6-13 are implemented. Protected APIs include request create/list/get/submit/decision/cancellation, direct booking, reservation lifecycle and extension operations, meetings/participants, share-link management, and the internal occupancy provider. The sole deliberately unauthenticated Booking route is `GET /api/v1/public/meetings/{token}`. Current Identity authorization and caller-token-propagated Organization, Room, and Scheduling checks govern protected operations. Requests and direct bookings validate current policy; approval-required direct bookings create only `PENDING_APPROVAL`; confirmed reservations, occurrences, and meeting data are transactional. S6-12 makes keyed request/direct-booking, extension, and share-link creation replay-safe, enforces explicit cancellation replay matching, and returns conflicts for changed payloads. S6-13 adds a protected occupancy snapshot provider and transactionally persisted, versioned occupancy events with an at-least-once outbox relay. See the S6-12 and S6-13 sections below for idempotency and event-delivery semantics.

Recurring acceptance uses the persisted Scheduling RRULE and IANA timezone, with Scheduling's one-year/365-date bounds. Booking validates every evaluated occurrence against the same-day timezone-local interval, the effective room policy, Room's existing protected maintenance-period API, and Booking-owned occupancy before writing. If any occurrence requires approval, the whole series uses the existing pending-approval workflow; the greatest applicable release buffer is used consistently for the series. The user-approved `reservation_occurrence` table stores one row per evaluated local date, and its PostgreSQL GiST exclusion constraint remains the final concurrent-conflict barrier. One transaction creates the series reservation, all occurrence rows, decision, meeting, organizer participant, and request transition. Scheduling and maintenance conflicts reject the series before writes with occurrence-specific stable errors; Booking occupancy conflicts roll back the whole series and return `ROOM_OCCUPANCY_CONFLICT` with affected local dates in the shared error message. PostgreSQL exclusion conflicts and deadlocks during overlapping writes normalize to that same stable conflict. Request idempotency and locked request state prevent duplicate acceptance.

Identity returns trusted display data only for authorized actions. Booking derives actor identity and evaluates current permissions, privilege, and building/department scope; caller-supplied actor, request type, approval result, and status are never authoritative. Caller tokens propagate to Identity, Organization, Room, and Scheduling, and unavailable or inconsistent authoritative results fail closed. A global interceptor protects every `/api/v1/**` handler. Reservation transitions are row-locked, timestamps are server-generated, and terminal states cannot be reopened. The approved nullable `reservation.completed_at TIMESTAMP WITH TIME ZONE` column is required iff status is `COMPLETED`, enforced by Flyway V3. Half-open reservation and occurrence occupancy includes the release buffer; PostgreSQL GiST exclusion constraints remain the final overlap barrier. Lifecycle, cancellation, and extension APIs are protected Booking routes only. Extensions retain their previous-end snapshot and decision history and revalidate owner-service policy/occupancy under locks. S6-11 share-link behavior is documented below. The protected S6-13 occupancy provider is documented below; its internal route is not Gateway-routed or included in public OpenAPI.

## S6-13 occupancy provider and event relay

- `POST /api/v1/internal/availability/occupancy` accepts `roomIds`, a positive half-open `startsAt`/`endsAt` range, and `contractVersion: "v1"`. It is protected by the same Identity-backed bearer interceptor as every Booking `/api/v1/**` operation, is hidden from generated public OpenAPI, and has no API Gateway route.
- A successful shared `ApiResponse` includes a query snapshot timestamp and exactly one entry for each requested room, including rooms with no active occupancy. Returned active occurrence intervals are finite half-open ranges from Booking-owned `reservation_occurrence.occupied_period`; they are returned un-clipped and already include the configured release buffer. Adjacent half-open intervals do not overlap.
- Invalid versions, duplicate/missing room IDs, invalid time bounds, malformed/non-finite intervals, and occupancy query failures do not claim availability. Query failures return stable `503 BOOKING_OCCUPANCY_UNAVAILABLE`; actionable database exceptions are logged server-side. Scheduling additionally rejects stale or incomplete snapshots and fails closed.
- Focused verification passed 21/21 tests: occupancy service (4), Booking application/PostgreSQL integration (8), and authorization interceptor (9), with zero failures, errors, or skips.
- Flyway V7 adds the user-approved service-local `booking_event_outbox` table; Booking writes one `booking.occupancy.changed` v1 UPSERT per confirmed/extended occurrence and REMOVE per active occurrence during cancellation, inside the same database transaction as the occupancy change.
- The scheduled relay claims pending rows with PostgreSQL `FOR UPDATE SKIP LOCKED`, publishes persistent JSON messages to `roomiq.events.v1` with routing key `booking.occupancy.changed`, and marks delivery only after a correlated positive confirm with no mandatory return. Failures persist the attempt count, exception type, and capped exponential retry time; rows are retained for retry and repeated failures are logged at error level.
- Delivery is at-least-once if a process fails after broker confirmation but before the outbox transaction commits. Consumers must deduplicate by `eventId`; equal `reservationVersion` events are all meaningful for recurring occurrences, while strictly older versions can be ignored. Scheduling has no event consumer and continues to use the fresh synchronous occupancy snapshot as its authority.
- Focused S6-13 outbox/transaction verification passed 20/20; the full Booking reactor passed 138/138, Identity 53/53, common-web 6/6, and the full 11-module backend reactor passed 311/311, all with zero failures, errors, or skips.

## S6-09 cancellation APIs

- `POST /api/v1/booking-requests/{requestId}/cancel` cancels an eligible request only when it has no reservation; it retains the request and appends cancellation history.
- `POST /api/v1/reservations/{reservationId}/cancel` cancels the whole reservation series, retaining its records while transactionally releasing every recurrence occurrence. Partial-occurrence cancellation is not exposed.
- Both routes require bearer authentication and current Identity authorization. Identity returns the current actor and one of `OWNER`, scoped `ADMIN`, or global `SYSTEM_ADMIN`; a caller cannot supply the actor or scope.
- For reservations, Booking loads the current effective Room rule using the caller token. `cancellationDeadlineAt` is the reservation start less the configured `cancellationDeadlineMinutes`. The owner may cancel through the exact deadline; after it, only an authorized administrator may cancel with a nonblank override explanation. The deadline snapshot and override are persisted. An unavailable or inconsistent effective rule fails closed.
- Owner cancellations use reason code `USER`; administrator cancellations use a non-`USER` reason code. Repeated calls return the original history result. State transition, history insert, and occurrence release are one transaction.
- The user-approved Flyway V4/ERD change makes the reservation exclusion constraint conditional on status not being `CANCELLED`/`RELEASED` and adds `reservation_occurrence.occupancy_active` defaulting true. The occurrence GiST exclusion applies only to active rows; cancellation marks all series occurrences inactive without deleting buffered half-open occupancy history. This allows later rebooking while retaining the database overlap barrier.
- No Booking cancellation API is configured on the Gateway.

## S6-10 extension APIs

- `POST /api/v1/reservations/{reservationId}/extensions` creates a pending extension for the authenticated reservation organizer. The optional `Idempotency-Key` replays only a request with the same organizer, reservation, and requested end; key reuse with different request data returns `IDEMPOTENCY_KEY_CONFLICT`.
- `POST /api/v1/booking-extensions/{extensionId}/decision` permits a currently authorized, in-scope non-requester to approve or reject. Self-decision is denied. Rejection records actor, time, and optional comment without changing occupancy.
- `POST /api/v1/booking-extensions/{extensionId}/cancel` permits the requester to cancel a pending extension; the extension row is retained as history.
- Recurring reservations are not eligible and fail with `RECURRING_RESERVATION_EXTENSION_UNSUPPORTED`. At most one pending extension can exist for a reservation. A previous-end snapshot prevents stale approval.
- Approval revalidates current Scheduling constraints and Room policy using caller-token owner APIs, requires a single occurrence matching the stored reservation, recomputes the current release buffer, and checks both reservation and occurrence occupancy excluding the reservation being extended. The existing reservation start is not re-screened against a new-booking advance window; current duration, calendar, room, maintenance, release-buffer, and occupancy constraints are still validated. Reservation and occurrence rows are locked before the extension row; updates, decision history, and both buffered occupied ranges commit or roll back together. The existing PostgreSQL exclusion constraints remain the final overlap barrier; conflicts return `ROOM_OCCUPANCY_CONFLICT`.
- No migration or ERD change was made. These routes are bearer-protected by the `/api/v1/**` guard and are not configured on the API Gateway.

## S6-08 meeting and participant APIs

- `GET /api/v1/meetings/{meetingId}` returns a shared `ApiResponse<MeetingResponse>`.
- `GET /api/v1/meetings/{meetingId}/participants` returns the authorized participant list in a shared response envelope.
- `POST /api/v1/meetings/{meetingId}/participants` adds a required/optional internal participant (`userId`) or external participant (`externalEmail`, `displayName`). Internal names are derived from Identity and internal accounts must be active and assigned to the meeting building. External participants are accepted only when the persisted booking request's `externalGuests` flag is true; that flag was validated against the Room-owned rule before booking acceptance. New participants start `INVITED`; caller-supplied internal names and invitation statuses are rejected.
- `DELETE /api/v1/meetings/{meetingId}/participants/{participantId}` removes only non-organizer participants.
- PRIVATE reads are allowed to the active organizer and scoped Booking reviewers. INTERNAL adds active users currently assigned to the same building. PUBLIC visibility does not grant these APIs unauthenticated or same-building access; public-card access is available only through an active share token. Participant reads use the same meeting visibility decision, and participants are not loaded if authorization fails.
- Participant writes are restricted to the organizer or a reviewer with current approval authority in the meeting building. Booking obtains meeting owner/scope facts from its own persisted records and propagates the caller bearer token to Identity. Meeting and participant routes are bearer-protected and are not configured on the API Gateway.
- Participant identity duplicates are checked while holding a pessimistic lock on the meeting row. Organizer attribution, reservation/meeting one-to-one ownership, and meeting-participant schema remain unchanged; no migration or ERD modification was made.

## S6-11 meeting share links

- `POST /api/v1/meetings/{meetingId}/share-links` requires the protected bearer guard and current Identity meeting `MANAGE` authorization. It permits only an `APPROVED` booking request with a `CONFIRMED` reservation and obtains the active building's IANA timezone from Organization using the caller token.
- Tokens contain a versioned 256-bit HMAC-SHA-256 output. Their stable derivation uses the authenticated Identity creator UUID, operation/version scope, idempotency key, and a separately configured secret key ring. Raw tokens are returned only by the protected create/replay response; Booking stores only each token's SHA-256 hash. Link revocation uses protected `POST /api/v1/meeting-share-links/{shareLinkId}/revoke`, rechecking the same meeting-management scope and persisting a server-generated revocation time.
- `GET /api/v1/public/meetings/{token}` is the only intentionally unauthenticated Booking data route. It accepts only token-shaped values, uses a row lock to serialize reads with revocation and view-count updates, and treats invalid, expired, and revoked tokens identically. A public card contains exactly `title`, `startAt`, `endAt`, `timezone`, and `organizerDisplayName`; IDs, agenda, instructions, contact data, participant data, location, and all other fields are excluded. The stored IANA zone formats the original reservation instants without changing them.
- Public reads are limited to 60 requests per client address per minute with a bounded 10,000-client in-process fixed-window table. Because limits are instance-local, deployments should also apply edge/gateway limits when S11 introduces routing. No other Booking route bypasses bearer authentication.
- S6-11's approved `meeting_share_link.timezone VARCHAR(64) NOT NULL` is populated from Organization; Flyway V5 refuses to invent timezones for legacy rows. S6-12 adds only the separately approved nullable `idempotency_key VARCHAR(128)` and uniqueness on `(created_by_user_id, idempotency_key)` in Flyway V6. Nullable legacy keys remain valid.

## S6-12 retry and replay behavior

- `POST /api/v1/meetings/{meetingId}/share-links` now requires an `Idempotency-Key` header containing 1-128 ASCII characters matching `[A-Za-z0-9._:-]`. Equivalent calls by the same authenticated creator return the same link ID, expiry, and deterministically reproduced token with `replayed: true`; the first response has `replayed: false`. Same-key reuse with another meeting or expiry returns `409 IDEMPOTENCY_KEY_CONFLICT`. Existing expiry, revocation, and public-read behavior is unchanged; replay never un-revokes an existing link.
- Configure `BOOKING_SHARE_TOKEN_KEY_RING` as comma-separated `version=base64url-secret` entries and `BOOKING_SHARE_TOKEN_ACTIVE_KEY_VERSION` as the version used for new links. Every decoded secret must contain at least 32 bytes. Store this configuration in a secret manager, not source control. For safe rotation, deploy the new active key while retaining old versions until all links created with them no longer need idempotent replay. Missing, invalid, or insufficient key material fails closed; Booking never mints a replacement token on replay when the original hash cannot be reproduced.
- Request, direct-booking, and extension creation serialize same-key retries with PostgreSQL transaction-scoped advisory locks and retain existing unique database constraints as the final barrier. Equivalent request/extension payloads replay their existing resource; different payloads return stable `409 IDEMPOTENCY_KEY_CONFLICT` errors. Cancellation replay returns the recorded result only for the same authorized actor and equivalent reason/override; altered retries return `409 CANCELLATION_REPLAY_CONFLICT`. Decision and lifecycle operations retain their existing one-decision/state-transition locks and stable conflicts.
- S6-12 verification passed: focused replay selection 66/66, full Booking suite 125/125, Identity 53/53, common-web 6/6, and the full 11-module backend reactor 298/298. All suites had zero failures, errors, or skips.

## Ownership and constraints

- Booking owns requests, approval decisions, reservations, occurrence occupancy, meetings, participants, extensions, share links, and the authoritative occupancy snapshot. Request and extension creation idempotency is enforced.
- Booking must use Identity, Organization, Room, and Scheduling owner APIs for authoritative cross-service data and decisions. It must not read or write another service's database.
- Confirmed reservation occupancy and concurrent same-room overlap prevention belong to Booking. Each `reservation_occurrence` stores a half-open interval including the configured release buffer; its GiST exclusion constraint is the final same-room concurrency barrier. The reservation range has its own GiST exclusion constraint for direct/single-occurrence reservations; `reservation` remains the series-level record and keeps its first-occurrence compatibility range.
- Approval-time overlap checks use Booking-owned occurrence data; the PostgreSQL occurrence exclusion constraint is the final concurrent-write barrier. The decision, series reservation, every occurrence, meeting, organizer participant, and request transition are committed or rolled back together.
- Booking's future internal occupancy provider is a dependency of Scheduling availability. Until implemented, candidate-producing availability searches fail closed.
- All Booking business operations require server-side authorization except the narrowly scoped implemented public share-token read. Stage 11 owns Gateway routing.
- The decision endpoint and reservation lifecycle operations are protected by the `/api/v1/**` bearer/Identity authorization guard and are not configured on the API Gateway.
- `POST /api/v1/bookings/direct` is protected by the same guard, resolves current Identity authority before owner-data validation, rechecks VIP eligibility from the authoritative Room result, and applies the active room's approval requirement to Admin, Super Admin, and Secretary initiators alike. It is not configured on the API Gateway.
- `POST /api/v1/reservations/{reservationId}/check-in` and `/complete` require current Identity authorization and persisted organizer/building/department facts. Identity allows an organizer only within their current scope, a lifecycle manager only within assigned building scope, or a global system administrator. The server sets lifecycle timestamps; invalid state transitions return `RESERVATION_STATE_CONFLICT`. Neither route is configured on the API Gateway.
- The approved ERD must not be changed without explicit user approval. Any demonstrated need for an ERD change must be proposed for approval before editing it.
