# Booking Service

## Current status

S6-01 through S6-09 are implemented; final S6-09 regression verification is in progress. Protected APIs include `POST/GET /api/v1/booking-requests`, `GET /api/v1/booking-requests/{id}`, `POST /api/v1/booking-requests/{id}/submit`, `POST /api/v1/booking-requests/{id}/decision`, `POST /api/v1/booking-requests/{requestId}/cancel`, `POST /api/v1/bookings/direct`, reservation check-in/completion/cancellation under `/api/v1/reservations/{reservationId}`, and the meeting/participant APIs described below. Creation validates request data and current Organization, Room, and Scheduling owner data before storing a `DRAFT`; only its active requester can submit it, which revalidates current policy and transitions it to `PENDING_APPROVAL`. Scoped Admin/Super Admin approval and rejection record one decision per request, with Identity-derived actor/time and an optional comment. Requesters cannot decide their own requests. Approval revalidates current Identity authorization, Organization, Room, Scheduling constraints/rules, and Booking-owned occupancy; within one transaction it stores the decision, creates a confirmed reservation using the current release buffer, and creates a PRIVATE meeting with the requester as accepted organizer participant. Rejection records the decision and state without creating a reservation or meeting. The direct-booking route supports authorized Admin/Super Admin and eligible Secretary callers. The active Room rule applies irrespective of initiator: when `approvalRequired=true`, only a `PENDING_APPROVAL` request is created, with no reservation or meeting; a different authorized approver must decide it. When approval is not required, Booking revalidates owner data and atomically confirms the reservation, each bounded occurrence, and private meeting.

Recurring acceptance uses the persisted Scheduling RRULE and IANA timezone, with Scheduling's one-year/365-date bounds. Booking validates every evaluated occurrence against the same-day timezone-local interval, the effective room policy, Room's existing protected maintenance-period API, and Booking-owned occupancy before writing. If any occurrence requires approval, the whole series uses the existing pending-approval workflow; the greatest applicable release buffer is used consistently for the series. The user-approved `reservation_occurrence` table stores one row per evaluated local date, and its PostgreSQL GiST exclusion constraint remains the final concurrent-conflict barrier. One transaction creates the series reservation, all occurrence rows, decision, meeting, organizer participant, and request transition. Scheduling and maintenance conflicts reject the series before writes with occurrence-specific stable errors; Booking occupancy conflicts roll back the whole series and return `ROOM_OCCUPANCY_CONFLICT` with affected local dates in the shared error message. PostgreSQL exclusion conflicts and deadlocks during overlapping writes normalize to that same stable conflict. Request idempotency and locked request state prevent duplicate acceptance.

Identity returns trusted display data only for authorized actions. Booking derives actor identity and evaluates current permissions, privilege, and building/department scope; client-supplied actor, request type, approval result, and status are never authoritative. Booking forwards the caller bearer token to Identity, Organization, Room, and Scheduling and fails closed on missing, denied, inconsistent, or unavailable authoritative results. A global interceptor protects every `/api/v1/**` handler, including `OPTIONS`. Check-in is allowed only for a `CONFIRMED` reservation and sets `checkedInAt` from the server clock; completion is allowed only after check-in and sets `completedAt` from the server clock. Requests do not accept actor IDs or timestamps. The transitions are row-locked and terminal `CANCELLED`/`RELEASED` reservations cannot be reopened. The approved nullable `reservation.completed_at TIMESTAMP WITH TIME ZONE` column is required iff status is `COMPLETED`, enforced by Flyway V3. No automatic missed-check-in or overdue status transition/release occurs. Reservation and occurrence occupancy remains half-open and includes the release buffer (five minutes by default); PostgreSQL GiST exclusion constraints remain the final overlap barrier. Lifecycle and cancellation APIs are service-level protected routes only, with no API Gateway route. Expiration processing, extensions, share links, and the Booking occupancy provider remain future Stage 6 requirements.

## S6-09 cancellation APIs

- `POST /api/v1/booking-requests/{requestId}/cancel` cancels an eligible request only when it has no reservation; it retains the request and appends cancellation history.
- `POST /api/v1/reservations/{reservationId}/cancel` cancels the whole reservation series, retaining its records while transactionally releasing every recurrence occurrence. Partial-occurrence cancellation is not exposed.
- Both routes require bearer authentication and current Identity authorization. Identity returns the current actor and one of `OWNER`, scoped `ADMIN`, or global `SYSTEM_ADMIN`; a caller cannot supply the actor or scope.
- For reservations, Booking loads the current effective Room rule using the caller token. `cancellationDeadlineAt` is the reservation start less the configured `cancellationDeadlineMinutes`. The owner may cancel through the exact deadline; after it, only an authorized administrator may cancel with a nonblank override explanation. The deadline snapshot and override are persisted. An unavailable or inconsistent effective rule fails closed.
- Owner cancellations use reason code `USER`; administrator cancellations use a non-`USER` reason code. Repeated calls return the original history result. State transition, history insert, and occurrence release are one transaction.
- The user-approved Flyway V4/ERD change makes the reservation exclusion constraint conditional on status not being `CANCELLED`/`RELEASED` and adds `reservation_occurrence.occupancy_active` defaulting true. The occurrence GiST exclusion applies only to active rows; cancellation marks all series occurrences inactive without deleting buffered half-open occupancy history. This allows later rebooking while retaining the database overlap barrier.
- No Booking cancellation API is configured on the Gateway.

S6-07 verification passed: the focused Booking lifecycle selection passed 37 tests, Identity passed 48, common-web passed 6, and the full 11-project backend reactor passed 244 tests, with zero failures, errors, or skips.

## S6-08 meeting and participant APIs

- `GET /api/v1/meetings/{meetingId}` returns a shared `ApiResponse<MeetingResponse>`.
- `GET /api/v1/meetings/{meetingId}/participants` returns the authorized participant list in a shared response envelope.
- `POST /api/v1/meetings/{meetingId}/participants` adds a required/optional internal participant (`userId`) or external participant (`externalEmail`, `displayName`). Internal names are derived from Identity and internal accounts must be active and assigned to the meeting building. External participants are accepted only when the persisted booking request's `externalGuests` flag is true; that flag was validated against the Room-owned rule before booking acceptance. New participants start `INVITED`; caller-supplied internal names and invitation statuses are rejected.
- `DELETE /api/v1/meetings/{meetingId}/participants/{participantId}` removes only non-organizer participants.
- PRIVATE reads are allowed to the active organizer and scoped Booking reviewers. INTERNAL adds active users currently assigned to the same building. PUBLIC visibility does not grant these APIs unauthenticated or same-building access; public-card access is deferred to S6-11. Participant reads use the same meeting visibility decision, and participants are not loaded if authorization fails.
- Participant writes are restricted to the organizer or a reviewer with current approval authority in the meeting building. Booking obtains meeting owner/scope facts from its own persisted records and propagates the caller bearer token to Identity. Meeting and participant routes are bearer-protected and are not configured on the API Gateway.
- Participant identity duplicates are checked while holding a pessimistic lock on the meeting row. Organizer attribution, reservation/meeting one-to-one ownership, and meeting-participant schema remain unchanged; no migration or ERD modification was made.

## Ownership and constraints

- Booking owns requests, approval decisions, reservations, occurrence occupancy, meetings, and participants. Request creation idempotency is enforced; cancellation, extensions, share links, and the authoritative occupancy snapshot remain future Stage 6 work.
- Booking must use Identity, Organization, Room, and Scheduling owner APIs for authoritative cross-service data and decisions. It must not read or write another service's database.
- Confirmed reservation occupancy and concurrent same-room overlap prevention belong to Booking. Each `reservation_occurrence` stores a half-open interval including the configured release buffer; its GiST exclusion constraint is the final same-room concurrency barrier. The reservation range has its own GiST exclusion constraint for direct/single-occurrence reservations; `reservation` remains the series-level record and keeps its first-occurrence compatibility range.
- Approval-time overlap checks use Booking-owned occurrence data; the PostgreSQL occurrence exclusion constraint is the final concurrent-write barrier. The decision, series reservation, every occurrence, meeting, organizer participant, and request transition are committed or rolled back together.
- Booking's future internal occupancy provider is a dependency of Scheduling availability. Until implemented, candidate-producing availability searches fail closed.
- All Booking business operations require server-side authorization except the narrowly scoped public share-token read, if approved and implemented. Stage 11 owns Gateway routing.
- The decision endpoint and reservation lifecycle operations are protected by the `/api/v1/**` bearer/Identity authorization guard and are not configured on the API Gateway.
- `POST /api/v1/bookings/direct` is protected by the same guard, resolves current Identity authority before owner-data validation, rechecks VIP eligibility from the authoritative Room result, and applies the active room's approval requirement to Admin, Super Admin, and Secretary initiators alike. It is not configured on the API Gateway.
- `POST /api/v1/reservations/{reservationId}/check-in` and `/complete` require current Identity authorization and persisted organizer/building/department facts. Identity allows an organizer only within their current scope, a lifecycle manager only within assigned building scope, or a global system administrator. The server sets lifecycle timestamps; invalid state transitions return `RESERVATION_STATE_CONFLICT`. Neither route is configured on the API Gateway.
- The approved ERD must not be changed without explicit user approval. Any demonstrated need for an ERD change must be proposed for approval before editing it.
